## Overview

Enterprise-grade IAM, API Security, and AI Security company website. Static single-page application deployed on **integrauth.com** via GitHub Pages.

**Core Services**: AI & Agent Security (agent authentication, non-human identities, MCP security & secure MCP libraries, FGA/ReBAC, AI integrations), Enterprise IAM, API Security Gateway, Cloud Integration (AWS/Azure/GCP), Enterprise SSO

**Brand line**: "Identity & Security for All — Humans, Machines, RPA bots & AI Agents" (two-line hero tagline; updated 2026-07-13, was "...for Humans, Machines & AI Agents" from the AI-first rebrand, 2026-07)

**Tech Stack**: HTML5, CSS3, JavaScript ES6+, jQuery 3.7.1, Bootstrap 5.3.3, Font Awesome 6.4.0

**Deployment**: **Cloudflare Workers** (`wrangler.toml` + `src/worker.ts`), cut over from GitHub Pages 2026-08. The Worker serves the repo root as static assets (`[assets] directory = "."`, `run_worker_first = ["/api/academy/*", "/auth/*"]`, `not_found_handling = "404-page"`, `html_handling = "auto-trailing-slash"`) and runs the Academy API at `/api/academy/*` plus the OIDC Relying Party at `/auth/*`. **`run_worker_first` must list every prefix `src/worker.ts` dispatches on** — a prefix handled in the Worker but missing there is answered by the asset server first and 404s on a route that looks correctly implemented. The front end still has no build step (hand-written HTML/CSS/JS + the existing minify commands); only the Worker is TypeScript, bundled by Wrangler. A committed `routes` block (`{ pattern = "integrauth.com", custom_domain = true }` + the `www` twin) — integrauth.com and www.integrauth.com are served directly by this Worker now, same `custom_domain` pattern the sister `integrauth/lab` repo already used for lab.integrauth.com. `workers_dev = true` is (re-)enabled as of 2026-08-01, but ONLY so `ci-deploy`'s Smoke probe / signing-key continuity steps have a URL that isn't behind the zone's Bot Fight Mode — nothing else links to it, no real traffic is meant to reach it, and `isAllowedOrigin` (api.ts) already accepts it via its pre-existing same-origin branch. GitHub Pages is retired (Settings → Pages disabled; the root `CNAME` file removed as dead weight, no longer meaningful once this repo isn't a Pages source). Every push to `main` deploys straight to production — `CF_TOKEN` needs `Workers Routes:Edit` + `DNS:Edit` + `Zone:Read` on the integrauth.com zone in addition to `Workers Scripts:Edit` + `D1:Read`, added at cutover. Local dev: `npm run worker:dev` (never bare `wrangler dev` — the assets dir IS the repo root, so wrangler's own `.wrangler/` state retriggers its watcher and reload-loops; see the gotcha comment in wrangler.toml). Security headers: `_headers` covers static asset responses, `src/lib/server/security.ts` covers API responses — keep the two in sync.

**Analytics** (2026-07-18): Cloudflare Web Analytics beacon (`static.cloudflareinsights.com/beacon.min.js`, zone-wide token `fa2d8aba…36b2` — the same token sunnahfast already used) appended before `</body>` on all 11 pages (support/privacy/cancellation have NO closing `</body>` tag — minifier stripped it — so the snippet sits at EOF there). Same token rolled out to all product/tool/demo repos. Pageviews/referrers/Core Web Vitals only — NO custom events by deliberate choice (Akhil, 2026-07-18; academy progress/cert/click stats would need a first-party Worker, parked). View in CF dashboard → Analytics & Logs → Web Analytics, filter by hostname. Academy is hash-routed, so lesson navigation = one pageview.

**URL style**: ALL internal links are extensionless (`/academy`, `/privacy`, `/#contact`, `/` for home) — GitHub Pages resolves `/academy` → `academy.html`, and so does the Worker's asset server (`html_handling = "auto-trailing-slash"`, which additionally 307s `/academy.html` → `/academy`). Never link `*.html` directly; canonicals and sitemap.xml are extensionless too.

### Accounts, shared SSO & the Academy API (2026-07-28)

> **[`docs/ACCOUNTS-ARCHITECTURE.md`](docs/ACCOUNTS-ARCHITECTURE.md)** is the quick-reference for this section: an ownership table (what's this repo's vs the Lab's), a "where do I make a change" lookup, the secrets table, and deploy order — kept short and current on purpose. **[`docs/HANDOFF-academy-sso.md`](docs/HANDOFF-academy-sso.md)** is the full build/audit history behind it (why the design is what it is, four adversarial re-audit rounds, what each found). Update the architecture doc whenever ownership, secrets, or the auth surface change; the prose below stays the authoritative detail. **[`docs/LEARNING-PLATFORM-BLUEPRINT.md`](docs/LEARNING-PLATFORM-BLUEPRINT.md)** is a third, different thing: the app-agnostic *pattern* distilled out of all of this (identity → progress sync → curriculum → labs → exam → certificates, in build order, with a 40-item mistake list) for reuse in other apps. It is deliberately NOT kept in lockstep with this repo — don't update it for an ordinary change here, and don't treat it as a source of truth about current behaviour.

The Academy was anonymous until this change; it now has **optional accounts**, and the account is **shared with the sister product at lab.integrauth.com** (`integrauth/lab` repo) — same user record, same physical D1 database (`lab-db`, bound as `DB` in wrangler.toml).

**SIGN-IN IS OIDC, NOT A SHARED COOKIE (redesigned 2026-07-30 — read this before touching auth).** The first design shared ONE session cookie between both apps (`__Secure-ia_session` with `Domain=.integrauth.com`). That was rejected on security grounds and reverted before it ever deployed. Cookie identity is `(name, domain, path)` and the `__Secure-` prefix only demands TLS — it does **not** restrict who may *set* the cookie (`__Host-` does, which is exactly why `__Host-` forbids `Domain`). So any of the ~30 sibling `*.integrauth.com` hosts (27 free-tool subdomains, the product apps, the 3 demos) could have replied `Set-Cookie: __Secure-ia_session=<attacker token>; Domain=.integrauth.com` and overwritten a visitor's session: session fixation (victim's progress, real name and certificates land in the attacker's account) plus an unclearable forced logout, and the token was transmitted to all ~30 hosts on every request. **Never reintroduce a cross-subdomain session cookie.** Instead: each app holds its own `__Host-` cookie and integrauth.com is an **OIDC Relying Party** against the Lab's OpenID Provider (Authorization Code + PKCE S256).

Two corollaries that are easy to get wrong, both found by re-audit on 2026-07-30:

- **The sibling subdomains are still SAME-SITE with us**, because "site" means the registrable domain. `__Host-` stops a sibling *writing* our cookie; it does nothing to stop a sibling *spending* it, and `SameSite=Lax` withholds nothing between same-site origins. So the Origin allowlist + `application/json` requirement in `guardStateChanging` (api.ts) is **load-bearing CSRF defence, not belt-and-braces** — an earlier comment claimed Lax had made it redundant, which would have justified deleting it. Don't.
- **Cookie-name selection keys on the HOSTNAME, not the URL scheme.** `sessionCookieName` returns the unprefixed dev name only for `localhost`/`127.0.0.1`. Keying it on `url.protocol !== 'https:'` (the original) correctly refused the dev name over HTTPS but happily *served* it to a plaintext `http://integrauth.com` request — and a cookie with no `__Host-` prefix is one any sibling can set with `Domain=`, reopening the exact fixation hole above. Nothing in either repo forces HTTPS at the zone level and our HSTS omits `preload`, so first-ever contact was genuinely exposed.

- **Ownership split**: the Lab owns the `users` and `sessions` tables *and* the entire account lifecycle (email OTP signup/login, its own logout, revoke-all, TOTP step-up, account erase) — plus it is the OpenID Provider. This repo owns its OWN sessions in `website_sessions` (Lab migration 0052) behind cookie `__Host-ia_web_session`, minted only at the end of an OIDC callback. It READS the Lab-owned `users` table (permitted, read-only: `validateSession` joins it for `status` — so a disabled or erased account stops working here on the next request — and for the email the navbar shows). It never touches the Lab-owned `sessions` table at all any more. Never run migrations from this repo against `lab-db`, and never write a Lab-owned table from here.
- **RP surface** (`src/lib/server/auth.ts` + `oidc-rp.ts`, routed via `run_worker_first`): `GET /auth/start` (PKCE verifier + `state` + `nonce` in a short-lived `__Host-ia_oidc_tx` cookie, then redirect to the Lab's `/authorize`), `GET /auth/callback` (exchange at `POST /oidc/token` with `client_secret_basic`, verify the ID token against the Lab's JWKS incl. `nonce`, mint our session), `GET /auth/session` (who-am-I; also the only route that re-issues the session cookie), `POST /auth/logout`, `POST /auth/logout-all`, `POST /auth/sessions/revoke`, `POST /auth/backchannel-logout` (OIDC Back-Channel Logout 1.0 — the Lab calls it on sign-out and we revoke by `oidc_sid`; it is deliberately exempt from the CSRF Origin guard because it is a server-to-server call authenticated by a signed `logout+jwt`, which is strictly stronger). Client id `integrauth-website`, scope **exactly** `openid email` — keep it equal to the Lab's seeded grant scope or returning users get a consent screen instead of a silent round-trip. No access token is retained and no refresh token is requested: nothing here calls the Lab's API after login, and the ID token already carries `sub` + `email`.
- **Sign-in UX is a FULL-PAGE REDIRECT, not a popup** (client migrated by request, pre-2026-08-20; this doc previously described the popup as current). `signIn()` in academy-auth.js navigates the tab to `/auth/start?mode=redirect`; the callback 302s straight back with no interstitial page, the reload re-renders everything against the new session, and cross-tab propagation rides the `acad_auth_session_v1` localStorage `storage` event. There is no `window.open`, no timeout, and no poll anywhere in academy-auth.js any more. The SERVER still fully supports `mode=popup` (self-closing page + `acad_auth_event_v1` localStorage handshake — the constant is still duplicated in `auth.ts` and `academy-auth.js`, keep them equal) — it's just unused by this client; the COOP `same-origin` headers on both apps are why the popup design needed the localStorage handshake in the first place (the browser severs `window.opener` once the popup goes cross-origin). Two things that still surprise people: (1) being signed in at the Lab does **not** automatically sign you in here — the OP has no `prompt=none` and its `frame-ancestors 'none'` rules out the hidden-iframe trick, so it costs one click (with an existing grant the authorize step approves itself). (2) The exam widget needs no sign-in callback: the redirect reloads the page, so it re-renders from scratch on the way back in.
- **Config**: `LAB_ISSUER` + `OIDC_CLIENT_ID` are non-secret `[vars]` in wrangler.toml. `IA_WEBSITE_OIDC_SECRET` must hold the **same raw value** as the Lab's env var of the same name (the Lab stores only its SHA-256, so it can never be read back or compared). Provision it as **one GitHub Secret — organisation-level, shared to both repos** — and each repo's CI mirrors it into its own Worker on every deploy, so rotating is "change it in one place, redeploy both". **Neither side ever generates it**, and both now REFUSE to: a value either CI invented would be one the other doesn't know, and since a generated Wrangler secret is masked out of the log and unreadable afterwards, nobody could tell the other side what to match. (The Lab's `provision-cf.sh` used to generate one as a last resort; because the Lab's `IA_WEBSITE_REDIRECT_URIS` is committed, that made `websiteClientConfigFromEnv` non-null and seeded a live confidential OIDC client whose secret was unknowable — sign-in then 401s `invalid_client` until someone sets the org secret and redeploys both. It now warns and leaves it unset.) Unset ⇒ `rpConfigFromEnv()` returns null ⇒ `/auth/*` answers 503 `sign_in_unavailable` (rendered as a self-closing HTML page in **both** popup and redirect mode — returning raw JSON left the popup's opener waiting out its full five-minute timeout, since only that page writes the localStorage handshake) and the account-free Academy keeps working.

  **All Worker secrets are provisioned from CI** (`.github/workflows/deploy.yml`, "Sync Worker secrets"), so nothing is set with `wrangler secret put` by hand. Three of them, with three different policies, and confusing them is how you break something: `IA_WEBSITE_OIDC_SECRET` is **mirrored only, never generated** (shared with the Lab — see above); `ACADEMY_PRIVATE_JWK` is **generated once and never rotated**, and is deliberately NOT overridable from a GitHub Secret, since the only reason to supply one by hand is to change it and changing it is the prohibited operation; `EXAM_IP_HASH_PEPPER` is **mirrored if a GitHub Secret of that name exists, otherwise generated**, and is freely rotatable — it re-buckets the exam rate limit, resetting in-flight 24-hour counts once, and nothing durable derives from it. The JWK's branch fails CLOSED on an unreadable/non-array `wrangler secret list` (an errored listing reads as "no secrets" and would silently rotate the signing key). A key longer than 32 bytes for the pepper is accepted but pointless: HMAC-SHA-256 pre-hashes any key over its 64-byte block size down to 32 bytes.

  **The never-rotate rule is ENFORCED, not just documented** (added 2026-08-01), because generate-if-absent cannot by itself distinguish "first deploy" from "the key was lost" — and the loss is silent: `/verify` keeps working (it is a D1 lookup, no crypto), so only the forwarded certificate JWTs quietly stop verifying, with no error on any side. `.github/cert-signing-key.kid` records the key's RFC 7638 thumbprint — public by construction (it is served in the JWKS) and in `.assetsignore`'s `.github` entry, so never published as a site asset. Two halves: the secrets step **refuses to generate** when the secret is absent but a kid is recorded (covers dashboard deletion, `wrangler secret delete`, and a `name`/`account_id` change in wrangler.toml, which silently means a *different* Worker with no secrets); and a post-deploy `Certificate signing key continuity` step compares the **live** JWKS kid against the recorded one, which catches what a name-only secret listing cannot — a secret that was *overwritten* rather than deleted still lists as present. An unreachable JWKS fails the check rather than passing it (the route fails closed when the key is unset, so a 500 there is itself the symptom). Deliberately **not** auto-committed on drift: recording whatever is live would document every accidental rotation as intended and the guard would never fire again. Accepting a rotation is meant to cost a reviewed commit to that file.

  **Why the sister Lab has the OPPOSITE rule, and don't copy one to the other.** The never-rotate rule here is a consequence of this repo having a **single-key JWKS**: `ACADEMY_PRIVATE_JWK` is the only key `certs.ts` knows, so there is no "retired but still verifying" state to rotate *into* — replacing the key is indistinguishable from deleting it. The Lab has a real multi-key lifecycle (`signing_keys`, its migration 0032: `current` → `retired` → `removed`), where a **retired key stays in the JWKS and keeps verifying everything it signed**, so rotation there is routine and safe *because retired keys are kept forever* — the Lab deliberately has no sweep for that table. Only its `POST /api/keys/:kid/remove` invalidates anything, and that now 409s with a count of affected certificates unless the caller re-sends `{"confirm":true}`. If this repo ever needs rotation, the fix is to grow the same multi-key lifecycle, NOT to swap the secret. And note what limits the blast radius on both sides: `/verify` is a **serial lookup in D1, not a signature check**, on this site (`GET /api/academy/certificates/verify/:serial`) and on the Lab (`GET /api/certificates/verify/:serial`) alike — so a lost or removed signing key means "forwarded JWTs quietly stop verifying", never "every certificate is void".

  Also required and easy to miss: **`ACADEMY_PRIVATE_JWK` now fails CLOSED.** If it is unset, certificate issuance and the JWKS route 500 rather than falling back to anything. The ephemeral-key fallback still exists for local dev but must be asked for via `ALLOW_EPHEMERAL_CERT_KEY=1`, which lives only in `.dev.vars` (gitignored, in `.assetsignore`, never uploaded by `wrangler deploy`) and therefore cannot reach production. The old unconditional fallback failed open in the worst way: it silently signed real certificates with a key that dies with the isolate and published a *different* public key per isolate, leaving every stored JWT unverifiable with no error anywhere. - **This repo's own tables**: `profiles` (first/last name + `name_locked_at`), `academy_lesson_progress`, `academy_quiz_progress`, `academy_last_position`, `academy_exam_attempts`, `academy_certificates`, `academy_progress_epoch` (Lab migration 0053) — all accessed through the parameterized helpers in `src/lib/server/store.ts`.
- **The reset epoch — why deleting progress needs its own channel.** The sync merges by UNION (read lessons are set membership, quiz masks are OR-ed), which is what makes it safe for an offline device to reconnect without deleting anything. The cost is that a union cannot express a DELETION, and "Reset track"/"Reset all" are exactly that. Before this, those buttons undid themselves *visibly*: the local marks cleared, the debounced sync fired ~800ms later, the server unioned every id straight back, and the checkmarks reappeared in front of the learner. Deleting server-side alone is **not** sufficient either — any other device holding the old progress re-uploads its stale copy on its next sync and the reset silently un-happens elsewhere. So: `academy_progress_epoch` holds a per-learner counter, bumped by `POST /progress/reset`. Every client stores it (`acad_epoch`) and echoes it on sync; a client whose epoch is behind has its payload **ignored** and is handed canonical post-reset truth plus the new epoch (`applyServerProgress` then REPLACES local state instead of unioning — unioning an empty server set into a full local one would change nothing, which is the whole trap). A *missing* epoch is treated as current, so older cached JS keeps syncing; a *higher-than-server* epoch is treated as stale, so a client cannot opt out of future resets by asserting a big number. `pushResetToServer()` in functions.js cancels the pending debounced sync **first** — that ordering is load-bearing. The epoch is re-checked INSIDE each merge write's own SQL statement, not only in the route's pre-check: the pre-check is a read followed by several awaited round trips, so a concurrent `/progress/reset` could land in that gap and the union writes would then resurrect the deleted rows stamped at the NEW epoch, where no later sync could detect or correct them.
- **API** (`src/lib/server/api.ts`, Hono, base path `/api/academy`): `GET/PUT /profile`, `GET /progress`, `POST /progress/sync`, `POST /progress/reset`, `POST|GET /exam/attempts`, `POST /certificates/issue`, `GET /certificates`, `GET /certificates/:serial/jwt`, plus two unauthenticated routes — `GET /certificates/verify/:serial` (public verification by serial) and `GET /.well-known/jwks.json` (public key for the certificate JWT; the **only** route that sends CORS, because the whole point is that a third party the learner forwarded a JWT to can verify it — a browser verifier cannot fetch it otherwise). Everything else requires the session cookie. Merge semantics are deliberate: read-lessons union (`INSERT OR IGNORE`), quiz masks bitwise-OR per track, last-position last-write-wins by caller timestamp — a stale device can never delete progress. `lastPosition.updatedAt` must be canonical ISO-8601 and not far-future: the merge decides the winner with a **string** comparison, so a merely-`Date.parse`-able value like `"Sat Jan 01 2050"` sorts above every real timestamp and would wedge the saved place forever. Row growth is bounded two ways — daily caps on exam attempts and certificate issuance, and `MAX_STORED_LESSON_ROWS`/`MAX_STORED_TRACK_ROWS` total ceilings on the progress tables, which have no daily cap because a real learner syncs constantly and whose ids the server cannot validate against a curriculum it does not hold. **Exam grading is server-authoritative** (`src/lib/server/exam.ts`): the client submits its per-question CHOICES (each option's original pre-shuffle index) for a 50-question sitting, and `POST /exam/attempts` grades them against `EXAM_ANSWER_KEY` and computes `score`/`passed` — the caller never sends a score. The old `legacy-local-pass` sentinel is GONE (a remembered pass carries no answers to grade), so the pre-account "claim my local pass" path is gone too — an anonymous learner re-takes after signing in; `acad_exam` is now only a local display hint. `EXAM_ANSWER_KEY` must stay in sync with `ACAD_EXAM_POOL`'s `a` values in `js/academy-labs.js` (keyed by the same stable question id); a drift surfaces as `invalid_answers`, never a mis-scored attempt. RESIDUAL (inherent, unchanged): the question text + correct index still ship in the public `academy-labs.js` bundle for the local "Review answers" screen, so the exam is unproctored and a determined reader can still look up answers — what's closed is that a passing *score* can no longer be fabricated with no exam. **The exam is limited to 3 attempts per rolling 24 hours, per ACCOUNT and per NETWORK** (`MAX_EXAM_ATTEMPTS_PER_DAY` / `MAX_EXAM_ATTEMPTS_PER_IP_PER_DAY`; was a 20/day abuse backstop). The per-account half alone caps nothing — accounts are free — so the network half is what makes the number mean anything; the cost is that one NAT (household, office, campus) shares one bucket, which is why the 429 carries `scope` (`account`|`network`) + `nextAttemptAt` + `Retry-After` and the UI says which limit was hit in so many words. The counting key is `academy_exam_attempts.ip_hash` (**Lab migration 0054**): a domain-separated SHA-256 of `CF-Connecting-IP`, HMAC-keyed when the optional `EXAM_IP_HASH_PEPPER` secret is set — read `src/lib/server/ip.ts` before describing it as anonymous, because an unpeppered hash of an IPv4 is brute-forceable. It is erased from rows older than the window by a `waitUntil` scrub on the write path (the attempt itself is kept forever), and the scrub MUST use the same window start the counts used or it deletes keys still being counted. `GET /exam/attempts` now returns `{attempts, limits}` — NOT a bare array — because the network half cannot be derived from a learner's own history; it deliberately reports only whether the network is exhausted (plus when it frees up), never a running count of other people's attempts. Still no general per-IP rate limiting on the other routes (needs a DO/KV).

There is **no OTP form and no Turnstile widget on this site any more** (the credentials are collected at the Lab; the `turnstile-site-key` meta tag was removed from all 11 pages). - **Local progress is scoped to the account** (`acad_owner` in localStorage holds the owning `userId`). On sign-in with a *different* `userId`, and on sign-out, `acad_read`/`acad_quiz`/`acad_pos`/`acad_pos_at`/`acad_exam`/`acad_epoch` are wiped before any sync runs. This is not tidiness: without it, on a shared machine learner A's progress synced into B's account on B's next login, and A's `acad_exam.passed` survived so B was offered "claim your prior pass" for a score they never earned — one click from a real, publicly verifiable certificate in B's name. If `acad_owner` is absent, existing local progress is treated as claimable (the intended "carry over my anonymous progress" path). One carve-out (added 2026-07-30): a PASSING `acad_exam` that the wipe would destroy is moved to `acad_exam_stash_v1` **bound to the owning userId**, and restored only when that same account signs back in — because the wipe also fires when a session dies server-side between grading and recording (revoke-all elsewhere, back-channel logout), which otherwise destroyed a full 50-question passing sitting with no recovery; a different account signing in neither sees nor can claim the stash. Three things about the stash are load-bearing and were all wrong in its first version (fixed round 4, same day): it is a **LIST keyed by owner**, not one slot, or the second learner to sign out on a shared machine destroys the first learner's still-unclaimed pass; the entry is **consumed only when it is actually restored** (or when what is already stored is itself a pass), because deleting it unconditionally meant a worthless anonymous *failing* sitting in `acad_exam` blocked the restore and then discarded the pass anyway; and the **account-switch branch stashes too**, not just the signed-out branch — a direct A→B transition with no confirmed signed-out state in between is reachable (a sign-in relayed by the `storage` listener, or a `/auth/start` deep link), and it was destroying A's pass outright. The reader still tolerates the old single-object shape so a mid-upgrade learner loses nothing.

  **The first sync after signing in has TWO entry points, and both must take the claim path** (fixed 2026-07-30, second re-audit). `claimAnonymousProgress()` — adopt the account's epoch, *then* merge — was reachable only from the `academy-auth-changed` listener, i.e. only on an identity *transition* seen while academy.html is open. But `academy-auth.js` loads on all 11 pages, so a learner can sign in from the home-page navbar and then open /academy, where the session is *already* signed in: no transition, no event, listener never runs. The boot path called `scheduleSync()` unconditionally, which posts epoch 0 — and any account that has ever been reset rejects that as stale and answers with post-reset truth, which `applyServerProgress` applies authoritatively, DESTROYING the anonymous progress it was supposed to carry over. Boot now takes the same `hasUnsyncedLocalProgress()` branch the listener does.

  **`academy-auth-changed` carries a `confirmed` flag.** Listeners that RENDER may use the cached session; listeners that WRITE (the sync) must act only on a server-confirmed one, for the same shared-browser reason as above. The boot event is fired with `confirmed:false`.

  **Two things about WHERE and WHEN this runs are load-bearing, and both were wrong until 2026-07-30.** (1) It lives in `reconcileProgressOwner` in **`js/academy-auth.js`**, not in `initAcademy()`. As an `initAcademy()` listener it never ran at all: `academy-auth.js` fires its forced `academy-auth-changed` synchronously while its deferred script executes, whereas `initAcademy()` registers listeners from jQuery's *asynchronously*-resolved ready callback — so the boot event had always already fired (deterministically, not as a race) — and `initAcademy()` no-ops entirely off academy.html, so a sign-in or sign-out from any other page's navbar reconciled nothing. (2) It runs **only on a server-confirmed session**, never on the localStorage cache. On a fresh browser profile the cache reads as signed-out, so reconciling against it wiped a *legitimate* learner's progress — including a passing exam record — on page load. Correspondingly, the first progress sync waits on `AcademyAuth.ready()` (which resolves after `/auth/session` answers, or after the probe says there is no server), because syncing against a cached guess is exactly how the previous learner's work lands in this learner's account.

  Sync ordering has two more guards worth knowing: `acadSyncGeneration` invalidates any response whose request predates a reset (an in-flight sync returning the *pre*-reset epoch was otherwise applied as authoritative, visibly undoing the reset and then flickering), and a **failed** reset now surfaces a toast with a retry instead of silently un-happening on the next union sync. **`acadSyncGeneration` is bumped by the ownership WIPE as well as by a reset** (round 4) — the wipe was the other event after which an in-flight response is not merely stale but harmful. Learner A finishes a lesson, the debounced sync goes out, A signs out mid-flight: the response (A's full progress *and* A's epoch, computed before the session ended) landed after the wipe and wrote all of it back into a signed-out, unowned browser. The restored `acad_epoch` then made `hasUnsyncedLocalProgress()` answer false, so learner B's sign-in skipped the claim path and plain-synced A's lessons straight into B's account, where the union made them permanent — the exact cross-account contamination the owner-scoping exists to stop, arriving through the one door it did not watch. A first sign-in carrying anonymous progress goes through `claimAnonymousProgress()`, which adopts the account's current epoch *before* merging — without that, signing in to an account that had ever been reset destroyed the anonymous progress it was supposed to claim.

### Boot loader & async CDN CSS (index.html + academy.html, 2026-07-14)

Both pages ship a full-screen boot loader (IntegrAuth-logo shield + pulse ring) that covers first paint through JS init, killing every flash class (unthemed light content, wrong-theme loader, old page lingering on nav). Four cooperating pieces — **keep them in sync**:

### Asset Minification

**Required Tools**: `clean-css-cli`, `terser`, `html-minifier-terser` (already in package.json)

**Minify CSS**:
```bash
npx clean-css-cli -o css/styles.min.css css/styles.css
```

**Minify JavaScript**:
```bash

```

**Minify HTML**:
```bash
npx html-minifier-terser --input-dir . --output-dir . --file-ext html \
  --collapse-whitespace --remove-comments --minify-css --minify-js
```

**After Minification**: Update cache version in index.html (e.g., `?v=1.7` → `?v=1.8`) for both CSS and JS references to ensure browsers load the new versions. And also update other html files like cancellation, privacy, support, terms, verify, mcp-security, ai-agent-security, api-security and 404 (404 references assets with absolute paths).

**Cache Busting**: Increment version number in:
- `<link rel="stylesheet" href="css/styles.min.css?v=X.X">`
- `<link rel="preload" href="css/styles.min.css?v=X.X">`
- `<script src="js/functions.min.js?v=X.X">`
- `<script src="js/academy-labs.min.js?v=X.X">` (academy.html only)
- `<meta name="acad-build" content="X.X">` in academy.html's `<head>`, AND `academy-version.txt` at repo root — both must match the new version, or the live-update toast (see below) fires spuriously on every visit.

**Minify labs JS**: `npx terser js/academy-labs.js -o js/academy-labs.min.js -c -m`

**Academy live-update toast** (added 2026-07-13): since GitHub Pages is static (no push channel), `initAcademy()` in functions.js polls `academy-version.txt` and compares it to the page's own `<meta name="acad-build">`, light on the server by design: ONLY on tab `visibilitychange`→visible and whenever `showLesson()` crosses into a new track (not on every lesson turn) — no standing interval (a 24h `setInterval` existed briefly, removed 2026-07-27 as unnecessary background polling for a page that's typically closed well before a day passes). On mismatch it shows a dismissible `.acad-update-toast` ("New lessons & fixes are available." + Reload button) — safe because all progress lives in localStorage, so a reload loses nothing. Forgetting to bump `academy-version.txt`/the meta tag on a deploy just means the toast won't fire for that deploy (not harmful); bumping them without a real deploy would falsely prompt everyone to reload, so always bump together with the real `?v=` cache-bust, from the same commit that ships.

> **EASY TO MISS — check this every time**: `academy.html` always loads `styles.min.css` and `functions.min.js`, so ANY commit that bumps either of those `?v=` numbers (not just Academy-labeled work — a CSS animation tweak, a nav fix, anything) is a real deploy from an open Academy tab's point of view. Bump `<meta name="acad-build">` in academy.html AND `academy-version.txt` to the same next number in that same commit, even if the change looks unrelated to Academy content. Skipping this doesn't break anything visibly (the toast just silently fails to fire), which is exactly why it's easy to forget — there's no error to catch it. This bit a real session on 2026-07-27: three commits bumped styles/functions versions for an Academy confirm-dialog fix and all three forgot the acad-build bump until asked directly.

## Quick Reference

**Key Functions**: `applyTheme()`, `initAcademy()`, `initServicesMarquee()`, `dismissBootLoader()` (there is no `toggleAndSaveTheme`/`initSmoothScrolling`/`initBootstrapComponents` — smooth scroll is CSS `scroll-behavior`, and no Bootstrap tooltip/popover init exists)

**Sections**: #navbar, #home, #solutions, #tools, #academy-promo, #products, #technologies, #clients, #process, #faq, #contact; academy.html: #acadHub, #acadReader, #acadDrill, #acadFlows, #acadChallenge, #acadExam, #acadAccount; landing pages: /mcp-security, /ai-agent-security, /api-security

**Verification**: See [.claude/skills/verify/SKILL.md](.claude/skills/verify/SKILL.md) — serve locally + Playwright across all 4 themes and 3 viewports; check FA glyphs render (CDN is FA 6.4.0) and no 404s

**Sign-in error handling**: `/auth/*` registers its own Hono `onError` that renders the CLOSING PAGE, not JSON — in (server-still-supported, client-unused) popup mode that page's inline script is the only thing that writes the `acad_auth_event_v1` localStorage handshake, and in redirect mode (what academy-auth.js actually uses) it is what carries the human-readable error back to a real browser tab instead of raw JSON. `/auth/callback` validates `state` BEFORE acting on the provider's `?error=` parameter: `fail()` clears the `SameSite=Lax` transaction cookie, so handling `error` first let any third-party page kill a victim's in-flight login by navigating them to `/auth/callback?error=access_denied`.

**No raw control bytes in source**: CI fails the build on them (`.ts/.js/.json/.html/.css/.yml/.toml`, excluding `*.min.*`). They make a file BINARY to grep and ripgrep, which then skip it in silence — `oidc-rp.ts` once shipped its open-redirect guard with literal NUL/US/DEL bytes instead of `\x` escapes, behaving identically and typechecking cleanly while being invisible to every text search run over the Worker. Use `\x`/`\u` escapes always. (CR is allowed: `js/functions.js` is CRLF.)
